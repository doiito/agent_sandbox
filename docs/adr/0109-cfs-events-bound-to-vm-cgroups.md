# ADR-0109：将节流事件绑定到实际 VM cgroup 再判断启动长尾

状态：Accepted（诊断方法，尚无新性能通过结论）；日期：2026-11-12；需求 PERF-03、QA-01、QA-03。

## 依据与决策

[rc87 千次](../../PUBLIC-QUALIFICATION.md#private-evidence)的 p95=7.894ms 已达到 8ms，p99=13.639ms 仍超过 10ms。1000 个存活 CPU 窗口中 505 个观察到节流增量，但窗口中位数为126.389ms，包含任务执行；25 个 >10ms 的请求中还有6个未观察到增量，不能据此证明准备长尾的根因。原 rc86 内核跟踪记录了 cfs_rq 指针，但该函数可在其他任务上下文中处理另一个组，当前 TID 和指针本身不能证明 cgroup 归属。

使用指定宿主实际 `/sys/kernel/btf/vmlinux` 的类型元数据，严格解析 `cfs_rq.tg → task_group.css → cgroup_subsys_state.cgroup → cgroup.kn → kernfs_node.id`，生成带 cgroup ID 的 throttle/unthrottle 元数据探针。所有指针、内嵌成员、匿名聚合及类型修饰都必须依据该份 BTF 核对；拒绝缺失、歧义、越界、位域或不符类型，不硬编码另一版本内核偏移。先完成[自评审](../../PUBLIC-QUALIFICATION.md#private-evidence)。

## 先验证观察器

只读查询能力并将 BTF 元数据保留在项目验证目录，不安装宿主依赖。原代码、签名包、CPU/NUMA/配额、持久归属和计时均不改。先在独立验证任务中建立私有受限 cgroup，用有界 CPU 工作产生确知节流；核对实际 cgroup inode、探针 cgroup ID、单调的 cpu.stat、同一 rq 的有序节流/恢复，以及一个未被限流的对照。这个控制不是 VM 性能样本。

探针使用独立 tracefs 实例/组，只记录内核元数据；不读用户缓冲、进程参数或秘密。原全局 trace 控制、其他探针及调度选项保持，持有原验证锁；时间、内存、日志和输出有界。任何丢失、探针 miss、身份无法关联或清理失败均保留并使观察器验收失败。失败先定位，只补未执行或受影响阶段，不重复完整 CI/E2E。

## 再用于原 API 的确切区间

观察器通过后，复用原已验证的元数据关联链和同一 rc87 签名包，保留正常 doctor、CPU2–5/NUMA0、128MiB/1vCPU、100000/100000、max_booting=2/health=1000ms、原七阶段。独立无跟踪/跟踪各128+5次原 API 请求，量化观察或时间顺序效应；不是正式千次或改变过的候选。按原请求/VM/PID代次/cgroup inode关联 request write、首段回复和持久审计，先构建跨边界完整节流区间再裁剪准备窗口。祖先或其他组的节流必须单列，不能凭调用线程冒充该 VM 的节流。

若证据支持配额周期造成具体等待，再设计保持平均 CPU 预算的定向干预；否则继续细分 guest/VMM/transport 和宿主持久化，不凭阶段名调参。旧 rc38 周期对照及 rc85 直连控制保留，不能冒充当前候选证据，也不忽略其负向发现。完整 warm 5/8/10ms、四路线千次、18项隔离/恢复、资源/长稳和原40项需求仍须满足。

当前只批准诊断方法和执行顺序，不登记性能达标或正式发布。

## 首个控制发现与受影响补验

r1 的限流子进程在迁入 cgroup 前已绑定 CPU2，迁组后最终亲和性却为 CPU0–47，按检查正确失败；不限流控制尚未执行。原 worker/业务归档和失败记录保留，独立检查确认两个私有组、实例和探针均清理。该轮在失败断言之前尚未导出原始 trace，不能追认 cgroup 身份已证明。

新 r2 只修正验证夹具：迁组完成后重新设置并读取实际亲和性，再放行子进程；任何已启用跟踪后的失败都先导出有界原始 trace 和统计再清理。新目录/任务 ID/探针组单列，原 r1 不写回或重放；两个控制按原配额和负载完成后再判断观察器，产品与 VM 配额不变。

## 身份控制结果与成功返回守卫

[2026-11-13 控制验收](../../PUBLIC-QUALIFICATION.md#private-evidence)：11项布局检查通过；r2 受限组21次节流与42个有序事件逐组一致，不限流组计数/事件均0，零丢失/miss，两个任务独立清理通过。原1242项程序及QEMU runner未变，未重复完整CI/E2E。

本控制只证明字段身份和该控制下的计数对应。当前 BTF 确认 throttle 函数返回bool，同版本上游代码存在预算重新可用而不执行节流的返回分支；因此通用观察器必须关联成功返回，不能把每个函数入口都当成有效节流开始。原API区间关联前先补这一守卫及否定控制，现阶段不调整产品配额或登记性能通过。

## 返回守卫的具体边界

2026-11-13：增加 throttle/unthrottle 的入口与返回配对，入口保留 BTF 核对的 cgroup ID、rq 和 throttled 状态；throttle 返回只读取 bool 的低8位，拒绝非0/1。按 `(CPU,TID)` 维护嵌套调用栈，避免把不同CPU的 idle TID0混为一个线程；不对入口按cgroup过滤而遗漏嵌套返回。返回false的尝试不生成节流区间，返回true后到对应unthrottle入口才是已确认节流区间，完整入口到恢复返回仅作外部包络。未配对的起止边界单列，不凭缺失事件补零或认定无节流。

先完成离线成功/false/嵌套/交错/边界/不一致否定用例，再以新ID补一次原两组有界CPU控制，核对四个探针零miss及计数。若自然窗口没有false返回，明确记录该路径仅有离线否定控制，不为等到false而重跑。源代码和BTF保持绑定，旧r1/r2不写回；成功后直接推进既定rc87 API两组，不增加正式千次或短性能pilot。

返回控制已通过14项离线检查和实际受限21次/不限流0次的四探针控制；自然false返回为0，不扩大其覆盖结论。原API诊断保留核心benchmark文件字节，以独立包装器在原owned_leases观察时附加实际cgroup目录FD的inode及父组inode，并前后核对PID代次；两组使用同一包装器。该额外观察及跟踪开销属于诊断，不能声称整条观察链字节不变或正式性能通过。七阶段、任务入口、工作负载和配额不改。

原CPU2–5元数据关联实例继续复用，新增的四探针CFS实例单独覆盖全部CPU以保留恢复回调；两实例均为mono时钟。先启CFS再启原关联实例，收尾反序，分别核对原全局状态。使用同一原包、两夹具各128+5次，补齐inode/请求/准备发送到首段回复的关联；未闭边界和其他cgroup事件单列。

## inode 编码缺口与定向补验

原API r1 两组266次请求均成功，原任务终态及独立清理通过；但原benchmark的validate_job采用字段白名单，包装器读取的顶层inode字段未写入最终样本。保留两组原始数据和该分析失败，r1只验证原API请求/时间，不追认inode归因完整。

新r2将实际目录FD观察到的inode及父组inode放入原白名单已保留的cpu_snapshot，不修改核心benchmark；新增回归必须经过实际validate_job及JSON序列化链确认字段存在。只补一次受影响的跟踪组128+5次，不重复r1已通过的无跟踪组。r2不与旧无跟踪组拼接成同包装器A/B、不登记新的观察成本因果比较或正式千次通过；原四路线/18用例/40项范围保持。
