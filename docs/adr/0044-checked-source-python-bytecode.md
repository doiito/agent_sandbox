# ADR-0044：保留源码语义的 Python 预编译缓存

状态：Accepted；日期：2026-11-02；需求 OSV-02、PERF-01、QA-01/02/05。

## 问题与证据

rc49 以无 ROFS 段缓存策略通过 128MiB 完整功能矩阵，64MiB 科学任务仍不通过。当前闭包主动移除所有 pyc，故每个一次性 VM 都要重新编译导入的 Python 源码。驻留诊断得到约 15MiB 的只读权限文件页，单独回收不足以弥补约 85MiB 分配器用量与 64MiB 的差距。tracemalloc 单次诊断记录约 35MiB 活跃 Python 分配，同时引入约 19MiB 追踪元数据；不能把它当作无探针 RSS。

## 采用方案

1. 用现有、固定版本的 CPython 3.12.16 为完全相同的源码生成 `optimize=0`、checked-hash 的 pyc，保留源码、文档字符串、断言、依赖版本和普通解释器清理。不使用 `-O`、`-OO`、冻结租户代码或复用已执行租户任务的 VM。
2. 首先建立项目目录内的独立实验闭包。原文件只读复用，清单与新增文件独立生成；不改写 canonical 资产或已验收 rc49。构建容器无网络，不增加目标机的安装依赖。
3. 逐项绑定源码 SHA256、字节码 SHA256、CPython magic、flags=3、source hash 与固定编译器；嵌入完整清单并验证 ELF 依赖闭包。不可只检查 pyc 文件存在。
4. 检查缓存确实被导入，源码变化使 checked-hash 缓存失效，assert 与 `__debug__` 仍有效。此处 Linux 结果仅作为构建参考。
5. 在同一内核、VMM、版本、启动策略和原 30 秒期限下，与 rc49 比较完整科学任务、导入阶段用量与 64MiB 结果。预编译可降低解析峰值，但不预先承诺降低活跃对象内存或达到 64MiB。
6. 若值得采用，再冻结签名候选，运行一次 CI 和受影响的完整冷/warm/异常/隔离矩阵。只有完整 64MiB 任务真实通过才能关闭该内存门禁；单次诊断不能关闭性能或生产门禁。

实施前[自评审](../../PUBLIC-QUALIFICATION.md#private-evidence)。不引入无数据支持的内核页回收实现；现有 ADR-0043 的所有权、TLB 与压力安全约束继续适用。

## 实验结果与剩余工作

[rc50](../../PUBLIC-QUALIFICATION.md#private-evidence) 已验证 1,111 项源码/字节码语义一致、缓存命中和失效、128MiB 完整 API 功能及正常清理；发现的无缓存块读取问题由 ADR-0045 修复。单对诊断中内存下降约 2.95MiB，时间缩短，均不作为合格性能证据；64MiB 完整任务仍 OOM。

[rc51](../../PUBLIC-QUALIFICATION.md#private-evidence) 已把固定编译器、预编译和逐项代码对象核对串入常规构建；v2 清单明确初始裁剪与最终缓存规则。一次完整本地 CI、128MiB 原 20 项 API、实际镜像中 1,111 项缓存内容及禁止源码重新编译后的完整科学任务均通过，方案采用。64MiB 仍 OOM/超时；合格性能、剩余组件版本与 CVE 扫描继续独立开放，Accepted 不代表这些门禁完成。
