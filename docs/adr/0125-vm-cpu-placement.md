# ADR-0125：按 vCPU 宽度分散 VM 的 CPU 放置

状态：Rejected（实现与功能控制通过，预定性能筛选未过；已恢复原产品源码）；日期：2026-11-17；需求 PERF-03、SEC-03、LIFE-04、QA-01、REL-04。

## 依据与边界

[ADR-0124 的完整关联](../../PUBLIC-QUALIFICATION.md#private-evidence)将 133 个实际 prepare G、Unix 收发线程、VM 代次和 vCPU 区间完整对齐。四个 >9ms 慢例的主要等待均在 VM 正文发布前，两个与同 vCPU 的配额节流和 R 等待重叠约 5.311/3.983ms，另外两个在 vCPU 调度上下文中约 8.388/7.829ms，不能当作纯 guest CPU。

目前单 vCPU VM 的所有 VMM 线程可在 CPU2–5 上并行，却共享每周期 100000us 的总 CPU 配额。vCPU、VMM I/O 和内核工作线程可提前消耗这一周期的配额；现有 1 CPU 平均上限没有约束瞬时并行宽度。为此评审一种可选的放置方式，并不宣称它解释所有慢例。保留原 rc92 正式 p99=14.245ms 的失败，不重复被否决的 max_booting=1、5ms 周期或固定 ready 等待。

## 决定

增加可选 `jailer.cpu_placement`，包含显式 `cpus` 集合及 `mode`（`shared` 或 `spread`）。未配置时完全继承现有行为，不额外要求 cpuset 控制器，也不假定宿主一定有 CPU2–5。`shared` 将 VM 放入整个指定集合，作为同程序对照；`spread` 每 VM 选择 vCPU 数量个不同逻辑 CPU，在指定集合中按已保留 VM 的占用数分散，稳定轮转打破同分。它是放置策略，允许 CPU 超分，不声称独占核或增加可用 CPU。

CPU 集合的解析、数量与请求大小有界，拒绝重复/重叠、负数、歧义格式和集合不足；配置最大 vCPU 数不得超过指定集合宽度。实际请求始终由宿主内部的资源预留决定 CPU 集合，不接受 HTTP/RPC/SDK 提供内部 CPU 列表。`cpu.max`、vCPU 数、内存、pids、UID/物理槽、父 CPU 集合与 NUMA 策略保持。单 vCPU VM 整组只能同时使用一个所选逻辑 CPU，避免通过增加配额处理突发。

CPU 分配计数并入现有共享 resourceLedger，在同一把锁下与物理内存、pids、身份槽一起预留；所有模板及 cold/warm/session 共用。启动失败回滚；成功启动后只有进程死亡、工作目录和 cgroup 成功回收才释放，cleanup_failed 保留原资源并封闭准入。释放幂等，不修改现有容量上限或添加固定等待。调用方配置深复制，放置策略进入既有模板/池键；进程 lease 保存分配集合并与内存所有权核对，重启仍先对账销毁旧 VM，不凭 lease 重新占用空闲 CPU。

通过已有 cgroup v2/jailer 路径为整个 VM 设置 `cpuset.cpus`，不逐线程调用需要新增能力的 sched_setaffinity，不增加 CAP_SYS_NICE。只在配置放置时要求父域已提供 cpuset，允许在项目自有 parent 内启用该控制器，不能改全局控制器或其他服务。启动前核对指定集合属于父有效集合及在线 CPU；probe/claim 核对实际有效集合与保留一致，不能静默扩大。内核 worker 随现有 cgroup 管理，故障保持拒绝并清理。

内核语义依据为 [Linux cgroup v2 官方文档](https://docs.kernel.org/6.1/admin-guide/cgroup-v2.html)：`cpu.max` 限制整组每周期总时间；`cpuset.cpus` 是请求集合，实际在线集合看 `cpuset.cpus.effective`。在线 CPU/父委派变化可能使请求失效并继承父集合，因此不能只核对写入值。指定机窄集合→扩大拒绝→恢复通过的实际内核控制已完成，自有 cgroup 回收且根控制器未变。

不直接改为所有宿主默认启用。先完成配置/并发计数/失败回滚/lease/池键和 cgroup 边界检查、受影响普通/race、双架构静态编译，再在指定机以相同实际 API/launcher 和原全功能 Linux 镜像、资源预算做实际 cpuset/生命周期控制。此前功能与原 40 项范围保持，不以基础载荷代替全功能验收。

功能控制通过后，最多一次预定 shared/spread ABBA，每臂 128 正式加 5 预热，共 532 个不同任务/VM；两模式使用同一程序和 CPU2–5/NUMA0、四物理槽、1vCPU、100000/100000、原七阶段、正常 doctor。完整记录每 VM 的实际窄集合、父集合/配额、ready 供给、HTTP/吞吐及 warm 分位数。正式资源检查应显式认识已声明的策略，逐项验证有效子集和宽度，不能把新值替换成旧的 `2-5` 字符串或忽略资源变化。

只有功能无回退、两次 B 方向可接受、合并 warm p95/p99/超限计数没有回退且供给/HTTP/吞吐没有实质退化，才进入完整新候选验收；不确定或变慢则保留失败并不采用。小样本不登记发布通过。新候选仍需完整 CI、双架构离线、ARM 无 NIC QEMU、指定机受影响功能/池场景及各必要正式路线千次，当前候选发布绑定门禁保持。

## 风险与评审

将 VMM I/O 与 vCPU 放在较少 CPU 上可能降低并行吞吐或增加 I/O 等待，尤其多租户超分场景；这是需要实测的成本。CPU 热插拔、控制器未委派、父集合收缩、跨模板计数分离或过早释放都可能破坏保证，须拒绝或保留资源，不能靠增大 CPU/延后测量来隐藏。见[实施前自评审](../../PUBLIC-QUALIFICATION.md#private-evidence)。

## 结果

同程序 shared/spread 的唯一 ABBA 完成532个不同任务/VM，业务、逐任务实际策略/资源、七阶段与独立清理通过。合并 warm p95 为6.378→4.369ms，但 p99 为11.193→11.222ms，两次 B 相对各自 A 的 p99 方向均未通过；ready wait p99 为198.603→224.041ms，增加12.808%，超过执行前10%筛选边界。不能把微小 p99 差异当作已证明变慢，但本批未证明所需尾部收益，按预定标准不采用，不重采直到变绿。

实验完整源码和6个执行程序先压缩归档并逐项核验，再只恢复10个改动文件和移除3个新增实验源文件；1355项产品身份精确回到已通过完整CI的发布绑定修复基线。原签名stage及发布绑定门禁没有回退。见[结果与恢复记录](../../PUBLIC-QUALIFICATION.md#private-evidence)。未生成新完整候选，原 rc92 正式 Linux warm p99=14.245ms 失败保持。
