# ADR-0101：warm pool 补 VM 并发的真实 API 对照

状态：Accepted（有界诊断，产品默认值及完整门禁待结果）；日期：2026-11-12；需求 LIFE-04、PERF-03、PERF-01、QA-03。

## 依据与决策

原 rc85 Linux warm 千次分布尾延迟未通过 5/8/10 ms；直连同 guest 的 48 次 prepare 最大仅 1.895 ms，未复现完整池环境的长尾。挂载微测量和增加固定 ready 等待也没有支持产品修正的证据。下一步只检查后台补 VM 并发与前台任务的竞争。

使用同一 rc85 签名包和同一次离线安装，保持原 Linux shell 工作负载、CPU/NUMA、128 MiB / 1 vCPU 配额、模板/容量/最低水位、健康间隔和补池速率。A 为 max_booting=2，B 为 1，固定 A1/B1/B2/A2 顺序，各 64 次请求及 5 次预热；原 benchmark 与准备器字节保持，不使用 diagnostic 覆盖实际 doctor。

各组之间停止本夹具 API/launcher，确认 MainPID=0、无 job/VM/cgroup 子节点、run_root owner 可取得且目录无进程引用，然后原子替换 config 中唯一的 max_booting 参数，再启动并等待原全部最低水位。保存每组配置、服务实例、实际 VMM 放置、边界、原始数据及最终 doctor。四组被测 VM 的 ID 必须全不相同。

配置替换保留原 root/API 专属组所有权与 0640 权限，file sync、rename 和目录 sync 后启动服务；逐组记录并核对权属。实施前复核发现初版验证工具没有保留 API 组读权限，该工具仅准备/上传、尚未执行；保留原输入，采用新 r2 目录和任务 ID 执行修正版。

同时报告 warm/完整 HTTP/池就绪等待分布、正常脚本 paced 吞吐、初次达到最低水位的时间、内存观察峰值、命中/回退及失败/超时/拒绝。该吞吐含校验、持久化及等待，不是饱和供给能力。即使 B 的局部启动变快，也不能忽略等待或吞吐下降；本批不满足每路千次要求，不登记 SLO。

顺序为本设计、[自评审](../../PUBLIC-QUALIFICATION.md#private-evidence)、冻结纯验证工具、单次持久任务和独立核验。全程串行持全局验证锁，不修改产品、guest 或宿主全局设置；最后核对原 90 个载荷，再清理重复安装、凭据、服务和专用 cgroup。失败保留原状态，不更换顺序或重放求通过。

## 实际结果

修正版 r2 的四组共 256+20 次全部成功，原载荷、唯一参数、配置权属、8 个服务实例和逐组零残留边界均独立核对。合并 A/B warm 为 3.694/9.116/11.261 与 3.728/8.440/11.161 ms，降低并发仍未满足尾延迟，同时 paced 吞吐下降 16.8%、ready_wait 中位数增加 30.7%。不采用并发 1，保持原配置与完整性能门禁；详见[验证记录](../../PUBLIC-QUALIFICATION.md#private-evidence)。
